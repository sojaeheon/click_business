# 외부 지표 기반 시장 캔들 및 봇 호가 개선

## 문제

- 기존 저부하 봇은 최초 시장가 주변에 매수·매도 5단계 호가를 만든 뒤 가격을 갱신하지 않았다.
- 사용자 체결이 없으면 1분봉이 같은 가격의 보합 캔들로 계속 저장되어 외부 지표의 흐름이 차트에 나타나지 않았다.
- 과거 방식처럼 봇이 스스로 체결을 대량 생성하면 Kafka, 매칭 엔진, Spark 부하가 커지고 가짜 거래량이 생긴다.

## 적용한 구조

1. 현재 게임 날짜의 `external_index` OHLC를 읽는다.
2. 게임 하루 600틱을 `시가 → 첫 극값 → 두 번째 극값 → 종가`의 세 구간으로 나눠 선형 보간한다.
3. 계산한 값을 100원 호가 단위로 반올림해 `market:reference-price:{itemId}`에 저장한다.
4. 기준가격은 매초 별도 표본 목록에 저장한다.
5. 사용자 체결이 있는 1분 구간은 실제 체결 OHLC와 실제 거래량을 사용한다.
6. 체결이 없는 구간은 기준가격 표본으로 OHLC를 만들고 거래량은 0으로 저장한다.
7. 봇 호가는 기준가격 주변의 매수 10단계, 매도 10단계를 유지한다.
8. 호가 중심은 10초마다 갱신한다. 낡은 가상 호가를 먼저 모두 제거한 다음 새 호가를 보충해 봇끼리 교차 체결되지 않게 한다.
9. 화면용 현재가가 최근 체결가 때문에 현재 스프레드 밖에 있으면 최우선 매수·매도 범위 안으로 보정한다.
10. 프런트엔드는 현재가와 같은 경계 호가도 표시해 최우선 호가를 숨기지 않는다.

외부 지표는 시장의 기준 경로만 제공한다. 실제 사용자가 봇 또는 다른 사용자와 거래하면 해당 체결가와 거래량이 캔들에 우선 반영된다.

## 자원 사용량 제어

- 봇은 품목별 최대 20개의 대기 주문만 유지한다.
- 재호가할 때 낡은 봇 주문을 먼저 제거하고 새 20단계를 즉시 보충해 호가창 공백을 줄인다.
- 단계당 목표 주문금액은 약 60만 원으로 맞춘다. 수량은 `목표금액 / 현재 호가`로 계산하고 단계별로 80~120%의 안정적인 차이를 적용한다.
- 외부 지표 DB 조회 결과를 게임 날짜 단위로 캐시해 품목별 매초 조회를 날짜당 1회 조회로 줄였다.
- 기준가격 갱신은 Kafka 거래 이벤트를 만들지 않으며 Redis 표본만 추가한다.
- 설정값은 `MARKET_BOT_REPRICE_INTERVAL_MS`로 재호가 간격을 조절할 수 있다. 기본값은 10,000ms다.

## 검증 결과

- Docker Gradle 빌드 성공
- 백엔드, 봇, 매칭 엔진, Kafka 3대, Spark 작업 모두 실행 중
- 품목 3개의 주문장에 매수 10단계와 매도 10단계가 복구됨
- 15초 연속 조회에서 화면 조건을 통과한 매수·매도 호가가 매번 각각 10단계로 유지됨
- 최종 봇 기동 후 여러 재호가 주기 동안 봇 간 체결 0건
- 무체결 1분봉 예시: 품목 3 `1,173,200 → 1,178,700`, 거래량 0
- 주문 DB consumer와 Redis consumer Kafka lag 0
- 점검 시 CPU: 백엔드 0.27%, 봇 7.19%, 매칭 엔진 2.41%, Spark worker 0.53%
- 점검 시 메모리: 백엔드 약 492MiB, 봇 약 460MiB, 매칭 엔진 약 473MiB

## 시험 데이터 정리 대기

첫 배포 검증 중 재호가 순서 문제로 봇 간 체결 71건이 발생해 `trade_history`에 가상 주문 측 행 142개가 남았다. 수정 후에는 재발하지 않는다. 사용자 거래 이력과 구분되는 정확한 시간 범위를 확인했지만, 거래 이력 삭제는 감사 데이터 변경이므로 별도 승인을 받은 뒤 정리한다.
